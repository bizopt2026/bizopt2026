# 올리기 음성 받아쓰기 (서버 안, faster-whisper) 설계

- 작성일: 2026-11-20
- 상태: 사용자가 방향을 정함 (서버 PC에서 받아쓰기, GPU 없음, faster-whisper, 모델 크기는 설정, 화자 구분과 재생 위치 이동은 2단계)
- 기준 문서: `2026-11-19-upload-first-intake-design.md` 의 9번("음성 파일을 위한 자리")을 이 문서가 실현한다.

## 1. 목적

회의·통화 녹음을 올리면 서버가 글로 받아써서 문서와 같은 길(활동 기록 정리)로 흘려보낸다. 녹음은 서버 밖으로 나가지 않는다.

## 2. 목표 / 하지 않는 것

### 목표
- 음성만 올려도 정리안까지 간다 (음성만 있는 묶음이 주 사용처).
- 받아쓰기는 서버 PC 안에서, GPU 없이 CPU로 한다. 엔진은 `faster-whisper`.
- 등록된 솔루션·고객·파트너 이름과 묶음 메모를 힌트로 줘서 고유명사를 덜 틀리게 한다.
- 오래 걸려도 화면은 진행(파일 이름, %)을 보여 주고, 사용자는 화면을 떠나도 된다.
- 서버가 도중에 꺼져도 이미 받아쓴 파일은 다시 받아쓰지 않는다.

### 하지 않는 것 (2단계)
- 화자 구분, 시간 표시를 눌러 재생 위치로 이동.
- 외부 받아쓰기 서비스 사용.
- 받아쓰기 정확도 보장. 틀릴 수 있다는 전제로 AI 정리 단계에서 다룬다.

## 3. 제약 조건
- 서버·시험 PC에는 NVIDIA GPU가 없다: `device="cpu"`, `compute_type="int8"` 고정.
- 모델은 인터넷에서 한 번 받아야 한다. 받는 곳은 `python -m app.cli stt-setup` 하나뿐이고, 서버 실행 중에는 인터넷에 접속하지 않는다 (`local_files_only`).
- 모델은 `data_dir/models/` 에 둔다 (사용자 프로필에 두지 않는다). 백업 대상이 아니다 (다시 받을 수 있다).
- faster-whisper 는 선택 설치(`pip install -e ".[stt]"`)다. 없어도 앱은 그대로 동작하고 음성은 "받아쓰기 필요"로 보관된다.
- 올리기 요청은 오래 걸리면 안 된다. 받아쓰기는 업로드 요청 안에서 하지 않는다.

## 4. 검토한 방식
- **A. 업로드 요청 안에서 받아쓰기 (기존 연결 지점 그대로).** 구현은 가장 쉽지만 긴 녹음이 브라우저 요청을 분 단위로 붙잡는다. 채택하지 않음.
- **B. 별도 받아쓰기 작업 종류를 대기열에 추가.** 깔끔하지만 묶음 상태·실패 처리·"다시 정리"와 이어 붙이는 코드가 늘어난다.
- **C. 기존 정리 작업(`intake_analyze`) 안에서 Claude를 부르기 전에 받아쓰기. (채택)** 상태 전이, 실패 복구, 버림 처리를 그대로 쓴다.

## 5. 흐름
1. 업로드: 음성 파일의 읽기 상태는 엔진이 있으면 `pending_transcript`(받아쓰기 대기), 없으면 `needs_transcript`(받아쓰기 필요). 요청에서는 받아쓰지 않는다. 이미 받아쓴 글이 저장돼 있으면 바로 `ok`.
2. 정리 시작: 읽을 수 있는 파일이 있거나 엔진이 있는 음성(`pending_transcript`)이 있으면 시작한다. 엔진이 없는 음성뿐이면 지금처럼 "읽을 수 있는 파일이 없습니다".
3. 정리 작업: Claude 호출 전에 받아쓸 음성(대기 또는 지난번 실패)을 번호순으로 하나씩 받아쓴다. 파일마다 ① 묶음이 아직 이 작업의 것인지 확인 ② 저장해 둔 글이 있고 모델이 같으면 재사용 ③ 아니면 받아쓰기 ④ 글을 작업 폴더에 `.md` 사본으로 쓰고 `uploads/intake/<묶음>/<저장이름>.transcript.txt` 에도 저장(첫 줄 `#model: <모델>`) ⑤ 읽기 상태 `ok` 또는 `failed`(+`read_error`).
4. 끝나면 `파일목록.md` 를 다시 쓴다 (받아쓴 파일의 종류는 "음성(받아쓰기)"). 읽을 수 있는 파일이 하나도 없으면 이유를 적어 묶음을 실패로 둔다. 있으면 Claude를 부른다.
5. 프롬프트 규칙: 받아쓴 글은 잘못 들은 낱말이 있을 수 있다. 등록된 이름과 분명히 같으면 구조화된 칸에는 등록된 이름을 쓰고 `reason` 에 밝힌다. 숫자·날짜는 조용히 고치지 않고 "(받아쓰기 확인 필요)"를 붙인다. 활동 원문은 받아쓴 글 그대로.

## 6. 설정 (`config.toml`)
| 키 | 기본 | 설명 |
|---|---|---|
| `transcriber` | `none` | `none` 또는 `faster-whisper` |
| `transcribe_model` | `small` | tiny, base, small, medium, large-v3, large-v3-turbo 또는 모델 폴더 경로 |
| `transcribe_language` | `ko` | 언어 코드, 자동은 `auto` |
| `transcribe_threads` | `0` | CPU 스레드 수, 0은 라이브러리 기본값 |
| `transcribe_max_minutes` | `120` | 이보다 긴 음성은 모델을 부르기 전에 길이만 보고 실패 (안내: 나눠서 올리기) |
| `transcribe_chunk_minutes` | `10` | 음성을 이 길이씩 나눠 받아쓴다 (메모리 한도) |

옵션: VAD 켬, `condition_on_previous_text=False`(반복 루프 줄임). 힌트(등록 이름 최근 순 + 메모, 전체 200자 이내)는 `hotwords=` 로 준다. `initial_prompt` 는 첫 30초 창에만 적용되고 `condition_on_previous_text=False` 이면 다음 창부터 비워지므로(개발 중 확인: 창마다 프롬프트 토큰 수 [3,0,0,0]) 쓰지 않는다. `hotwords` 는 모든 창의 앞에 붙고 라이브러리가 223 토큰에서 뒤를 자른다(그래서 최근 이름이 앞에 온다). 둘을 함께 주면 첫 창에 같은 글이 두 번 들어가므로 `hotwords` 만 쓴다. 조각마다 같은 힌트를 준다.
### 6.1 길이 확인과 조각 나누기 (메모리)
`model.transcribe(경로)` 는 파일 전체를 한꺼번에 읽고 VAD·특징 계산까지 마친 뒤에야 돌려주므로 메모리가 녹음 길이에 비례한다(개발 중 합성 음성으로 측정: 60분 음성에 최고 3384 MB. 모델 메모리 제외). 그래서 ① PyAV 로 파일을 열어 길이(컨테이너·스트림 정보, 모르면 읽으면서 확인)를 `transcribe_max_minutes` 와 견줘 모델을 부르기 전에 거절하고, ② 16 kHz 모노로 조금씩 읽어 `transcribe_chunk_minutes` 마다 끊어(조각 끝 10초 안의 가장 조용한 50 ms 칸에서 자름) 조각을 numpy 배열로 `model.transcribe` 에 준다. 시각·진행률은 조각 시작만큼 더하고, 조각이 끝날 때마다(글이 없어도) 진행을 알려 취소(버림)도 확인한다. 언어 자동(`auto`)은 첫 조각에서 정한 언어를 나머지에 쓴다. 개발 중 합성 음성으로 측정한 최고 메모리(모델 제외): 10분 조각 845 MB, 5분 조각 548 MB. 모델은 첫 사용 때 불러온 뒤 프로세스가 끝날 때까지 메모리에 계속 올라가 있다(`_MODELS`).

출력은 조각마다 한 줄, 약 60초마다 줄 앞에 `[12:00]` 표시. 화자 표시 없음.

## 7. 동시성과 대기열
- 받아쓰기는 프로세스 전체에서 한 번에 하나 (잠금). 워커가 여럿이어도 같다.
- 받아쓰는 정리 작업은 워커 스레드 하나를 오래 쓴다. 기본 `ai_concurrency = 1` 이면 받아쓰는 동안 다른 AI 작업(활동 정리, 제안 등)이 기다린다. **이 절충은 그대로 두고 운영 가이드에 적는다 (대기열은 다시 설계하지 않는다).**
- 워커가 둘 이상이면 작업을 집을 때 "받아쓰기가 필요한 정리 작업은 다른 받아쓰기가 도는 동안 건너뛰는" 검사를 한다. 그래서 받아쓰기 대기 때문에 워커가 묶이지 않고 짧은 작업이 계속 처리된다.
- 받아쓰기 시간은 AI 작업 제한 시간(`ai_timeout_s`)에 포함되지 않는다 (그 제한은 Claude 호출에만 적용).

## 8. 진행 표시
`IntakeFile.progress`(0~100)를 최대 2초에 한 번, 작업 트랜잭션과 별개의 짧은 쓰기로 갱신한다. 상태 조각(2초마다 조회)은 "음성 받아쓰는 중 · 파일 이름 · 37%" 와 "녹음 길이에 따라 오래 걸릴 수 있어요. 이 화면을 떠나도 됩니다."를 보이고, 끝나면 "AI가 파일을 정리하고 있어요". 받아쓰는 동안 "보통 1분 안에 끝납니다"는 보이지 않는다. 같은 쓰기 때 묶음이 버려졌는지도 확인해 받아쓰기를 멈춘다.

## 9. 실패 처리
- 파일 하나의 실패(오래됨·손상·엔진 오류·빈 결과)는 그 파일만 `failed` + 짧은 한국어 `read_error`. 자세한 원인은 로그에만.
- 음성만 있는 묶음이 실패하면 묶음도 실패(이유 표시). 문서가 함께 있으면 문서로 계속한다.
- "다시 정리"는 실패한 음성을 다시 받아쓰고, 끝난 음성은 저장해 둔 글을 쓴다. 모델 설정이 바뀌면 저장해 둔 글은 쓰지 않는다.
- 서버가 받아쓰는 도중 멈추면 기존 복구(`fail_stale_running`, `intake.recover`)가 묶음을 실패로 두고, "다시 정리"로 이어서 한다.
- 받아쓰는 중 묶음을 버리면 파일 사이 또는 진행 기록 때 알아채고 멈춘 뒤 작업 폴더를 지운다.
- 패키지·모델이 없으면 엔진은 "사용 불가"이고 점검 화면과 `check` 에 이유와 해결 명령이 나온다.

## 10. 데이터
`IntakeFile.read_error`(문자열, 비어도 됨), `IntakeFile.progress`(정수, 비어도 됨)를 `migrate.py` 가 시작 때 추가한다. 읽기 상태 값 `pending_transcript` 추가.

## 11. 확인하지 못한 것
- **개발 환경에서 모델을 받을 수 없어(모델 저장소 접속 차단) 실제 받아쓰기를 한 번도 돌려 보지 못했다.** 시험은 가짜 엔진으로 했고, 실제 라이브러리는 모델이 없을 때의 오류 처리까지만 확인했다.
- 한국어 정확도, 모델별 속도, 실제 모델의 메모리 사용(개발 중 합성 음성으로 측정한 값은 모델을 뺀 음성 부분뿐), 긴 녹음의 실제 소요 시간, Windows 에서의 모델 저장(링크 대신 복사)과 오디오 형식(m4a, wma 등) 지원은 서버 PC에서 `stt-setup`, `stt-test` 와 README 수동 확인으로 직접 확인해야 한다.

## 12. 수정 묶음에서 정한 것 (리뷰 반영)
- **PyAV 19:** faster-whisper 1.2.1 의 `decode_audio` 가 `av.open(metadata_errors=...)` 를 부르는데 PyAV 19 는 거절(TypeError)한다. 선택 설치에 `av<19` 를 묶었다. 조각 읽기는 이 인자를 쓰지 않는 자체 PyAV 코드라 PyAV 19 에서도 돌았지만(개발 중 확인), 라이브러리의 다른 경로를 위해 핀은 유지한다.
- **오류 분류:** 오디오 디코더(`av.error.FFmpegError` 계열, 메모리·입출력 제외)가 낸 오류만 "손상되었거나 지원하지 않는 형식"으로 안내하고, 나머지(TypeError·ImportError·AttributeError·MemoryError·OSError·모델 오류)는 "받아쓰기 프로그램 오류입니다 (종류)" 로 알리며 자세한 내용은 로그와 명령줄에만 낸다.
- **준비 확인:** 모델 폴더에 `model.bin`(비어 있지 않음), `tokenizer.json`, `vocabulary.*` 가 있어야 준비된 것이다 (라이브러리 1.2.1 에서 하나씩 빼 보며 확인; `config.json` 은 없어도 읽힌다). 준비 확인 결과는 부를 때마다 파일을 다시 본다.
- **엔진을 나중에 켠 경우:** `needs_transcript` 음성은 설명 화면의 안내와 "정리 시작/다시 정리" 로 `pending_transcript` 가 된다.
- **저장본:** 받아쓴 글 파일의 머리는 `#model:` 과 `#language:` 두 줄이다.
